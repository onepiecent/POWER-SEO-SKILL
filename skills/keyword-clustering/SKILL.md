# Keyword clustering: read real exports, group on request

Turns a very broad keyword file into **clusters** (each cluster = one blog post) and then **groups** (the clusters along the dimension you need). Reply in the user's language; keywords and deliverables stay in English.

## Workflow

1. **Receive the file and the request.** Establish: market (US/UK), the dimension to group by, filters (volume, KD, words to drop or keep) and the desired granularity. If something is missing, use the defaults and state the assumption (see the table below). Ask only when the request is genuinely ambiguous.
2. **First run with default settings plus the request:**
   ```bash
   python3 skills/keyword-clustering/scripts/cluster_keywords.py export.csv --out outputs --group-by occasion,recipient
   ```
   Several files or markets: `us.csv::us uk.csv::uk` (a file with a Country column is recognised automatically). Excel files (`.xlsx`, the default Semrush export) are read directly.
   **One-topic export** (a Semrush "thanksgiving day" file is broad match: it also contains Labor Day, Mother's Day...): keep the topic with `--only occasion=thanksgiving`. Typos of the topic word are fixed first, so `thanksgivng day` is kept.
3. **Read `outputs/cluster-report.md` first.** Check, in this order:
   - *Input*: are the encoding, delimiter and header row plausible; which columns were recognised; the volume source (real `volume`, GSC `impressions`, or Keyword Planner buckets read as ranges). *Source tool, market and sheets*: the tool detected, where each file's market came from (a column, `::us`, the file name, the Search Console Country filter, `--market`) and every sheet read or skipped. *Columns used as evidence* and *Ignored columns*: data the file has that was not used; if an important column is listed as ignored, map it with `--map`. Read every warning (GSC capped at 1,000 rows or without a country filter, a file-name market that disagrees with `--market`, grouping columns that are not used yet).
   - *Joined duplicates*: the same keyword from two files, or repeated rows of a positions export, is counted once (§2); `volume_sources` in `keyword-map.csv` lists every tool and value.
   - *Filters*: which keywords were excluded and why. Open `excluded.csv`, sort by volume and look for false exclusions (for example "boots" is no longer treated as a retailer; "mama bear shirt" is not Spanish). If something is wrong, edit `assets/noise-rules.json` or turn the filter off with `--no-noise-filter`.
   - *Spelling*: the corrections learned from the file (typos, split words such as `thanks giving`). `spelling-fixes.csv` lists **every** fix with the keywords it changed and the volume of both forms: a real word taken for a typo (`skirts→shirts`, `bedding→wedding`) has a sizeable `from_volume`. Turn off with `--no-respell` if one is wrong.
   - *Result*: lexical clusters, then clusters (posts) after merging question variants; the share of single-keyword clusters (>70% means the threshold is too strict or the data is very diverse: try `--granularity loose`); the theme table (sub-topics such as dates, history, meaning, activities, messages).
   - *Evidence coverage*: the share of keywords and volume with SERP URLs, Parent Topic, tool intent, SERP features, trend, traffic potential and ranking URL; the grouping basis of the clusters (`serp`, `parent_topic`, `lexical (not verified by SERP)`, `mixed`, `single`); the SERP-verified share of the volume; the linkage (seed); whether the posting-list or merge-candidates cap was hit. When most volume is grouped by words only, say so to the user: those groupings are a heuristic until checked on the SERP.
   - *Need conflicts*: keywords whose `need_source` starts with `conflict:` (the regex said shop, the tool's intent or SERP features say the reader is researching). They stay in the blog plan; decide each one.
   - *Unclassified*: if more than 15% of the volume, read `taxonomy-suggestions.csv` (frequent n-grams in unrecognised keywords), propose taxonomy additions (see `references/taxonomy-guide.md`), then re-run with `--extend-taxonomy`.
4. **Audit an SEO's grouping (`--prior`).** By default (`--prior-mode audit`) the SEO's groups are the starting point, not a constraint: the skill's rules are checked on every group and the grouping is changed **only on positive evidence**, every change in `seo-audit.csv` with its reason (`grouping_basis` `prior:audited`). Word similarity alone never splits an SEO group (two phrasings of one idea may share no word). The checks of this step (`kw_audit.py`):
   - `same_query`: two groups whose main keywords are the same query (same words after normalisation) or share >= `--serp-overlap` top-10 URLs: merged into the group that can win more traffic [Google: one page per query; Convention].
   - `duplicate`: a keyword listed in several groups stays where it is the main keyword, else in the group whose main shares most of its words.
   - `shop_member`: a pure shopping keyword (`buy ...`) is split out of a blog group (the topic map skips it).
   - `main_changed`: a member names the post instead of the SEO's main when it asks the same thing (same subject words, same word order, a phrasing at least as natural) and either the SEO's main has a year, or the member has 2x its volume, or the SEO's main is above the site's reach and the member wins 1.25x its winnable volume (below). An inverted tool phrasing (`christmas tree ribbon how to decorate`) never names a post.
   - `segment_modifier` / `tone_variant`: two groups the engine's word rule would merge whose mains differ by a segment word (how many, who, which character, decade or setting: `trio halloween costumes male`) are **kept apart**; by tone words only (`cute`, `short`, `scary`) on a list topic (jokes, captions) they are **merged** (`assets/taxonomy.json` `modifier_rules`, learnt from the SEO's SERP check: segment pairs 30 of 32 had different SERPs, tone pairs on jokes and captions 6 of 6 matched) [Research: SERP sample; Convention].
   - `possible_duplicate`: the other such pairs (tone words on other topics: `cute trio halloween costumes`): **not applied**, listed in the final plan's SERP To-do sheet.
   - `serp_apart`: with SERP data (`--serp`), two close mains that share fewer than `--serp-overlap` top-10 URLs stay two posts; `clusters.csv` `keep_apart_from` tells the topic map not to merge them either (a `keep_apart` decision does the same).
   - `export_topic` / `noise_flag`: export keywords in no SEO group that form topics of their own; SEO keywords that match a noise rule (kept, listed).
   The topic map then audits pillars, too-small groups and the hub (topic-map SKILL.md). `--prior-mode keep` keeps every group exactly as the SEO set it (`prior:seo`). The SEO's sheet may be one group per row (main + secondary list), **one keyword per row below its main** (a row with an empty Main cell continues the group above; its Volume/KD are that keyword's), a keyword + group column, or the team's final plan; a Kind / Category Kind column without a Thuộc Pillar column puts each Cluster under the last Pillar (or Kind-less head) above it. Every sheet is read; keywords above the first group are clustered, never dropped; a Semrush Keyword Strategy Builder export (Topic > Page > Keyword) uses the Page as the group.
5. **Keyword difficulty against the site's reach.** A high-volume keyword the site cannot rank for brings nothing, so every keyword gets a `winnable_volume` = volume x fit(KD) and a `kd_fit` label (`easy` up to the reach, `stretch` up to reach + 15, `hard` above, `unknown` without KD); clusters get `cluster_winnable`, `main_kd_fit` and `site_kd` (`kw_kd.py`). The reach is `--site-kd N` (the SEO's judgement), else measured (75th percentile KD of the keywords an organic-positions export says the site ranks top 10 for, >= 20 of them), else 30, the start of Semrush's "possible" band [Tool documentation: Semrush KB; the curve is a Convention]. A Semrush **Personal Keyword Difficulty** (already computed for the domain) is used row by row when present and compared with 49; an empty PKD cell falls back to the generic KD. The main keyword of a cluster may be a lower-KD phrasing of the same question that wins >= 1.25x the traffic (`seed_basis` "easier to rank (KD)"): a competitor's secondary keyword can be our main keyword. The topic map uses the winnable volume to choose hubs and rank posts.
6. **Back-check and decide.** Read `backcheck-report.md` and `backcheck.csv` (every run; one group per cluster as planned; each issue cites the real numbers and proposes one decision in `proposed-decisions.csv`, never applied as it is: a decisions file whose author is `proposal` is rejected). A keyword whose only evidence is word overlap is listed for a SERP check, never proposed for a move, and never a keyword bigger than the target group or a head term under a longer phrase that contains it; the engine's own clusters are not re-judged on words. Review `proposed-decisions.csv`, `spelling-fixes.csv` and `excluded.csv` (restore a false exclusion with `keep_keyword`, not by editing the shipped noise rules). Write the accepted decisions to `decisions.csv` (reason and evidence required) following the checklist in `printerval-blog-seo/SKILL.md`, re-run with `--decisions decisions.csv` and read `decisions-log-cluster.csv`: a `claude` decision the SERP or Parent Topic data contradicts is `rejected_by_data` (tell the user; the SEO checks the live SERP). Formats and rules: `references/backcheck-and-decisions.md`.
   **Review `merge-candidates.csv`** (cluster pairs near the merge threshold, with `evidence_type` lexical / serp / parent_topic, both volumes, needs, themes, cores and the guard fields that differ): read each pair, decide "merge / keep apart / leave", and record the decision for the user. When real SERP data (`serp_urls`) exists, trust it over vocabulary. `serp-check.csv` holds the largest borderline pairs and word-only groups (`--serp-check-max`, default 30); the final plan turns it, with the audit's possible duplicates, into the SERP To-do sheet: a short list of keywords to look up, then a re-run with `--serp` (`printerval-blog-seo/references/serp-check.md`). Your web search is not a Google SERP: never record overlap counts from it.
7. **Hand over** `clusters.csv` + `cluster-report.md` (+ `groups.md` when `--group-by` was used) with: the assumptions used, the real figures (read / excluded / joined / clusters), how much of the volume is SERP-verified, and the points that need a person's decision (`serp-check.csv`, need conflicts, doubtful spelling fixes). Next step: `topic-map`.

## Translating an SEO specialist's request into options

| They say | Option |
|---|---|
| "Only the US/UK market" / the file is for the UK | `file.csv::uk` or `--market uk` |
| "Group by recipient / occasion / interest / product" | `--group-by recipient` (or occasion, interest, product, style, craft) |
| "Group by occasion, then by recipient" | `--group-by occasion,recipient` (nested) |
| "Group by reader intent (ideas, how-to, comparison...)" | `--group-by intent` |
| "Group by my own groups: Family, Work, Pets..." | `--categories categories.json --group-by category` (see `examples/categories-example.json`) |
| "Only Mother's Day and Father's Day" | `--only occasion=mothers-day,fathers-day` |
| "Only keywords about dogs/cats" | `--only interest=dogs,cats` or `--include "\bdogs?\b" --include "\bcats?\b"` (several `--include` = or) |
| "Drop brand/competitor/free/pdf keywords" | `--exclude "\bfree\b" --exclude "\bpdf\b"` (retailers and brands are already excluded by default) |
| "Drop low-volume / very high-volume keywords / KD > 60" | `--min-volume 100`, `--max-volume 50000`, `--max-kd 60` |
| "Drop shopping keywords" | `--drop-shop` (by default they are only tagged `blog_fit=low`, not removed) |
| "Smaller / more detailed clusters" or "broader clusters" | `--granularity tight` / `--granularity loose` (or `--sim 0.7`) |
| "Group by sub-topic (dates, history, food, quotes...)" | `--group-by theme` (or `--only theme=history`) |
| "Do not merge 'when is X' with 'what day is X'" | `--no-consolidate` (keeps the lexical clusters) |
| "The file has a top-10 SERP column" | a `serp_urls` column; the script clusters by SERP overlap automatically (`--serp-overlap 4`) |
| "We checked these keywords on Google" | `--serp serp.tsv` (one row per result: keyword, url, market, position..., as `printerval-blog-seo/assets/serp-extract.js` copies it; or keyword + serp_urls): wins over the export's column; `kw_serp.py` |
| "The Ahrefs file has Parent Topic" | `--trust-parent-topic` to merge by that column |
| "The file name says UK but it is the US file" | `file.csv::us` (the file name wins over `--market`, with a warning) |
| "Give me more / fewer pairs to check on Google" | `--serp-check-max 50` |
| "A column has a different name" | `--map keyword="Top queries" volume=Impressions` |
| "Here is my grouping, check it and fill it in from this export" | `--prior grouped.xlsx::us export.xlsx` (repeatable; a grouped file is never auto-detected: always pass it with `--prior`); the grouping is audited and regrouped where a rule fails (`seo-audit.csv`) |
| "Keep my groups exactly as they are" | `--prior grouped.xlsx::us --prior-mode keep` |
| "Our site ranks for KD up to 40" / "we are a new blog" | `--site-kd 40` / `--site-kd 20` (else measured from a positions export, else 30) |
| "Apply what we decided" | `--decisions decisions.csv` (CSV, or .xlsx with a `Decisions` sheet; logged in `decisions-log-cluster.csv`) |
| "I want to save the settings and re-run" | `--request request.json` (see `examples/request-example.json`) |

**Complex requests** ("Mother's Day by recipient, Father's Day by interest"): run several times, each with its own `--only` and `--group-by`, write to different `--out` folders, then combine the results for the user. Unclear requests ("group it sensibly"): use the defaults and say what you chose and why.

Valid facets and values for `--only` and `--group-by`: `assets/taxonomy.json`. `intent` means `reader_need`: inspire, choose, how_to, solve, copy_ideas, info, shop.

## Supported file formats

Handled automatically: **Excel `.xlsx`/`.xlsm`** (every sheet with a keyword column is read and named in `source_file`; skipped sheets are listed; no extra library needed), a quoted cell with several lines (stays one cell), Vietnamese headers (NFC-normalised), UTF-8, UTF-8 with BOM, **UTF-16 + tab** (Keyword Planner, some Ahrefs exports), cp1252; description lines above the header (Keyword Planner); delimiters `, ; tab |`; numbers such as `1,234`, `1.234`, `1K`, `1.2M`, `1K - 10K` (a range: the lower bound is read and flagged as an estimate; change with `--range-mode mid`), `<10`, `35%`; Keyword Planner bucket values (`50`, `500`, `5000`... with empty monthly columns) are read as the same ranges [Research: observed in real exports]. Evidence columns are read too: tool intent (words, Semrush API codes, I/N/C/T, Ahrefs true/false columns), SERP features, Semrush Trend, Ahrefs SV trend, Keyword Planner `Searches: Mon YYYY`, Traffic potential, ranking URL and position. Rows of markets other than US/UK are excluded (`market:<code>`). A sheet named after a market (`US`, `UK keywords`) is read as that market; several sheets without one, read with a single `--market`, are reported. Real headers, details and pitfalls per tool: `references/export-formats.md`.

## How the script clusters (to explain and verify)

- **Normalisation:** lowercase, apostrophes removed (`mother's` -> `mothers`, `when's` -> `when is`), hyphens -> spaces, repeated words collapsed (`thanksgiving thanksgiving thanksgiving`), an assistant prefix dropped (`google when is thanksgiving` = `when is thanksgiving`), UK->US variants for matching (mum->mom, personalised->personalized, nan->grandma), years dropped (`2026`), simple plurals removed.
- **Spelling learned from the file:** a rare word within 1-2 letters of a frequent word is a typo (`thanksgivng`, `thankgiving` -> `thanksgiving`); two words whose joined form is the usual spelling are joined (`thanks giving`), also when a space was typed inside the word (`thanksgivi g`); a rare word made of a common pair is split (`whenis` -> `when is`); a cut-off last word of an autocomplete query is completed when one word clearly follows (`thanksgiving da` -> `thanksgiving day`). Only frequent words are targets, word forms (`celebrates`) are left alone, two real words are never glued (`is real` stays), and Spanish rows are ignored. `spelling_fixed=1` in `keyword-map.csv`.
- **Exact duplicates are joined first:** the same text in the same market from several files (or repeated rows) is one keyword; an exact volume beats an estimate, then the larger value wins; it is never summed (`volume_sources`, `kd_source`).
- Same-meaning variants within one market are merged next (word order, a year, a fixed typo); the version **without a year** names the pair when it has at least 20% of the volume (`when is thanksgiving`, not `when is thanksgiving 2026`). Variants and their volumes are kept in `variants` / `variant_volumes`.
- **The post's name (main keyword)** is never a keyword typed with a typo, and among phrasings with >= 80% of the top volume the clearly more natural one wins: `true story of thanksgiving` (1,300) over `real story thanksgiving` (1,600), `thanksgiving facts for kids` over `... for kindergarteners`. "Natural" is a word-pair model learned from the file's own keywords (`name_fluency` in `clusters.csv`); Semrush rounds volumes into steps, so such pairs are often tied.
- **Facet detection** with regexes in the taxonomy: occasion, interest, recipient, product, style, craft, and **theme** (the sub-topic of a one-topic export: dates, history, meaning, facts, food, activities, messages, world, events, gifts...). Know-how facets (sizing, care, materials) need a product context, so "turkey size" is not a sizing question. Every keyword gets a `reader_need` (from the rules, else from its theme) and a `blog_fit` (shop = `low`: pure shopping intent, left to the shop pages and content team). When the regex says shop only because a product word is present, but the tool's intent is informational or commercial, or the SERP has People also ask / a featured snippet / an AI Overview, the need is recomputed without that fallback and `need_source` records the conflict [Convention: vendor intent labels are hints].
- **Seed-based clustering** (the highest-volume keyword is the seed): at least N shared SERP URLs, or weighted Jaccard >= the threshold (words such as "gift", "ideas" and "best" weigh 0.3). Two keywords are merged lexically only when they share the **market, the intent group (inspire~choose count as one) and the same occasion / recipient (including implied: mother's day -> mom) / interest / product / theme**, and ask compatible things (their *cores* match).
- **One post per question (consolidation):** the *core* of a keyword is what is left once the topic, the theme's generic words, question words and stop words are removed (`when is thanksgiving`, `what day is thanksgiving 2026` and `thanksgiving 2026 date` all have an empty core; `is thanksgiving always on a thursday` has {thursday}). Clusters with the same guard and the same core become one post. Synonyms (`true/truth/real`, `pilgrims/1621/first`) are in `core_synonyms`. `--no-consolidate` turns it off.
- **How each keyword joined its cluster** is in `joined_by` (`seed`, `serp:<shared URLs>`, `parent`, `lexical:<similarity>`, `core:<core words>` for a consolidated question); `grouping_basis` and `serp_verified_share` in `clusters.csv` summarise it per post.
- **Performance:** inverted index + prefix filter. Each posting list is capped at about 3,000 entries, so the search is exact only while no list hits the cap: the report counts the cap hits (and says so when there are none). 150,000 synthetic keywords take about 85 seconds.

**Limits to state plainly:** vocabulary does not understand deep synonyms (two very different phrasings of one idea can land in two clusters; add them to `core_synonyms`); `cluster_volume` is a sum, so it is an upper bound (`cluster_volume_dedup` beside it counts variants that report the same volume once, an estimate); `lexical (not verified by SERP)` clusters are a heuristic until the SEO checks `serp-check.csv`; facet and theme regexes can miss new niches (see `taxonomy-suggestions.csv`); SERP overlap is more accurate but needs real SERP data for each market.

## Do not

- Do not invent volume or KD when the file has none; warn and explain the consequence.
- Do not merge US with UK (different SERPs, different vocabulary).
- Do not drop keywords silently: every excluded keyword must be in `excluded.csv` with a reason.
- Do not turn each keyword variant into a post (scaled content abuse); one cluster = one post.
